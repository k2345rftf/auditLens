## 1. Контекст

Модуль `loophole` находится в активной фазе развития. Функциональность «полный контент источников» реализована и покрыта тестами (319 passed в `tests/loophole`), но накоплен технический долг и есть архитектурные риски, которые юнит-тесты на SQLite не ловят.

**Ключевые метрики (на 2026-07-27):**

| Метрика | Значение |
|---|---|
| `.py` файлов в `src/bank_audit/loophole` | 37 |
| Строк `loophole.jsx` | ~65 000 |
| Строк `loophole.css` | ~32 000 |
| Тестов `tests/loophole` | 319 passed |
| Ошибок ruff в `src/bank_audit/loophole` | 120 (24 автоисправимых) |
| Ошибок mypy в `src/bank_audit/loophole` | 38 |
| Новых миграций (не в HEAD) | 2 (015, 016) |

**Критические риски, обнаруженные в коде:**

1. **Сессии БД в фоновых задачах.** `healer.py` и `runner.py` создают `asyncio.create_task`, который после выхода из request-контекста может пытаться писать через уже закрытую SQLAlchemy-сессию. Это приводит к «висячим» run-записям и неприменённым коммитам.
2. **FastAPI-антипаттерн `Depends(get_session)` в default-аргументах.** В `web.py` 9 эндпоинтов используют `session=Depends(get_session)`. В продакшене это даёт утечки/старые сессии, потому что сессия вычисляется при импорте, а не при запросе.
3. **Blind `except Exception`.** 49 срабатываний BLE001 подавляют ошибки и усложняют отладку.
4. **Healer пишет код без контроля.** `patch_parser` в `tools_nanobot.py` атомарно заменяет `parser.py`. Это допустимый инструмент самовосстановления, но автоматический heal не должен применять патчи без аудита.
5. **SQL guard на регулярках.** `_is_read_only_select` использует blacklist, который можно обойти через комментарии или строковые литералы.
6. **In-memory state парсеров.** `_RUNNING`, `_LOG_BUS`, `_LOG_TAIL` живут в RAM одного процесса. При рестарте приложения теряется runtime-информация.
7. **N+1 dedup в `runner.py`.** Каждый результат парсера проверяется тремя отдельными `SELECT`.
8. **Синхронный backfill.** `POST /records/backfill-content` блокирует HTTP-worker на `time.sleep`.

## 2. Решение

Провести рефакторинг четырьмя волнами, начиная с блокеров стабильности и заканчивая архитектурными улучшениями. Все изменения должны быть разбиты на маленькие, обозримые PR по принципу одна история — один PR.

### 2.1 Принципы, которые сохраняем

- **Greenplum 6:** без `PRIMARY KEY`/`UNIQUE`, дедупликация на уровне приложения.
- **SQL без ORM:** `sqlalchemy.text()`.
- **Gemini-совместимость nanobot:** схемы tools должны оставаться валидными для OpenAI-совместимых эндпоинтов, включая Gemini.
- **Безопасность:** READ-only SQL для агента, встроенные tools nanobot отключены, маскировка ПДн перед LLM.
- **Маленькие PR:** команда маленькая, поэтому каждое изменение должно проходить ревью за <30 минут.

### 2.2 Архитектурные решения

#### Решение 2.2.1: Request-сессия не передаётся в фон

Все фоновые задачи (`runner.wait`, `_heal_worker`, `scheduler.tick`, `collector.collect_once`, `refine_keywords`, `backfill`) открывают собственную сессию через `db.session()` на старте и закрывают её в `finally`. Request-сессия используется только в синхронной части HTTP-обработчика.

#### Решение 2.2.2: Heal с human-in-the-loop

- Автоматический `heal_tick` **не пишет** код. Он только диагностирует причину сбоя и формирует `patch_proposal`.
- `patch_parser` остаётся инструментом nanobot, но применяется только после явного подтверждения пользователя через UI/API.
- Все изменения кода парсера логируются в `loophole_action_log`.

#### Решение 2.2.3: SQL guard на AST

Заменить blacklist-регулярки в `audit_db_query` на разбор AST через `sqlparse` с проверкой: корневой оператор — `SELECT`; в запросе отсутствуют DML/DDL во всех CTE и подзапросах; `LIMIT` присутствует.

#### Решение 2.2.4: Фоновые задачи — через Celery/ARQ

Для `backfill`, `heal`, `collect`, `refine` вводится асинхронная очередь. В рамках MVP выбираем **ARQ**, потому что:
- проще Celery (нет брокера Redis на старте — можно использовать Redis уже имеющийся в стеке);
- нативная async/await поддержка;
- меньше инфраструктуры.

Если в проекте уже используется Celery — переиспользуем его. Окончательный выбор фиксируется в ADR после аудита существующей инфраструктуры.

#### Решение 2.2.5: Разделение API-слоя

`web.py` (812 строк) разбивается на подроутеры:
- `loophole/routers/records.py`
- `loophole/routers/chat.py`
- `loophole/routers/parsers.py`
- `loophole/routers/export.py`
- `loophole/routers/admin.py`

`loophole/web.py` остаётся точкой монтирования `APIRouter`.

#### Решение 2.2.6: Batch dedup в runner

В `runner.py` результаты парсера группируются в пакет; один `SELECT` проверяет все три ключа (`sha256`, `url`, `text_sha256`) сразу; новые записи вставляются одним batch INSERT.

## 3. Рассмотренные альтернативы

### 3.1 Очередь: Celery vs ARQ vs собственный worker

| Вариант | За | Против | Вердикт |
|---|---|---|---|
| **Celery** | Зрелый, много интеграций | Требует Redis/RabbitMQ, сложнее async-API, тяжёлая конфигурация | Использовать, если уже в проекте |
| **ARQ** | Лёгкий, async-нативный, совместим с Redis | Меньше экосистемы, чем у Celery | **Предпочтительный для новой инфраструктуры** |
| **Собственный asyncio worker** | Нет зависимостей | Самописное расписание, retry, мониторинг | Не использовать — изобретаем велосипед |

### 3.2 SQL guard: regex vs AST

| Вариант | За | Против | Вердикт |
|---|---|---|---|
| **Регулярки** | Просто, быстро | Обходится через строки/комментарии | Отказаться |
| **AST (sqlparse/pglast)** | Надёжно, проверяет структуру | Дополнительная зависимость, нужен fallback для сложных запросов | **Принять** |

### 3.3 Heal: автопатч vs human approval

| Вариант | За | Против | Вердикт |
|---|---|---|---|
| **Автопатч** | Быстрое самовосстановление | LLM может сломать рабочий парсер, security-риск | Отказаться от автоматического применения |
| **Human-in-the-loop** | Контроль, аудит | Медленнее, требует UI | **Принять** |

## 4. Последствия

### 4.1 Положительные

- Устраняется главный риск нестабильности в проде — закрытые сессии в фоне.
- Повышается безопасность: LLM не может больше автоматически менять код и SQL.
- Уменьшается нагрузка на БД за счёт batch dedup.
- API-слой становится тестируемым и обозримым.
- Линтер/типизатор становятся gate'ом CI.

### 4.2 Отрицательные / риски

- **Дополнительная инфраструктура:** ARQ/Celery требует Redis и отдельного worker-процесса.
- **Изменения в UI:** human-in-the-loop heal требует нового экрана «предложенные патчи».
- **Регрессии в тестах:** переход на batch-запросы и разделение роутеров может сломать существующие тесты, если идти большим PR.
- **Greenplum-совместимость:** batch INSERT и FTS-индексы должны быть проверены на реальном диалекте, а не только SQLite.
